# Microstepping Test Data v3

Reliable-identification campaign on the EVO dedicated controller: six
MRES/current configurations, each running the reference, conditioning,
Condition C (creep/settling), and Condition D (velocity-plateau sweep)
blocks. This revision holds the actual hardware run and a lightweight
processing pipeline built directly from the two raw files -- no
intermediate splice/aggregate data is kept in git (see "Layout" below).

## Layout

- `data/raw_local/SteppingSequenceID.csv`: raw Dewesoft IDS linear-encoder
  export (nm/count, tab-separated). Local-only, .gitignored (>50 MB) --
  it is a direct hardware capture, not regenerable, so keep a backup of it
  outside this repo.
- `data/raw_local/identification_controller_log.csv`: the EVO controller's
  own event log (one row per command/event) -- the authoritative source of
  block boundaries and configuration metadata.
- `scripts/run_identification_dedicated_controller.py`: copied from
  `../v2/scripts/`. This is the driver script that was actually run to
  produce the hardware data in `data/raw_local/` -- kept here for
  provenance alongside the data it generated, rather than only in v2.
- `scripts/plot_full_raw_sequence.py`: parses both raw files and renders
  `rendered_assets/full_raw_sequence.png` (all six runs) plus, per run,
  `rendered_assets/individual_subplots/run_0N_.../sequence_plot.png` +
  `sequence_data.npz`.
- `scripts/plot_block_montage.py`: renders, per run,
  `rendered_assets/individual_subplots/run_0N_.../block_montage.png` --
  a 10-panel montage in chronological order (BLOCK_0, C, then the 8 D
  plateaus ascending), each D panel with its own independent y-scale.
- `scripts/command_reconstruction.py`: shared "commanded trajectory"
  reconstruction used by `plot_block_montage.py`,
  `plot_block_montage_with_simulation.py`, and
  `simulate_block_responses.py` -- see "Controller-paced D-rate command
  reconstruction" below.
- `scripts/simulate_block_responses.py`: simulates the Rev 4.2 parallel
  LuGre + nonlinear-detent model against each block's reconstructed
  commanded trajectory, saving one `lugre_simulation.npz` per run --
  position plus motor torque, detent torque, and the three decomposed
  LuGre friction-port forces/torques (way, nut, sb), all as time series.
- `scripts/plot_block_montage_with_simulation.py`: clone of
  `plot_block_montage.py` with the simulated trace overlaid, saved as
  `block_montage_simulated.png`.
- `scripts/plot_torque_montage.py`: same 10-panel chronological layout,
  but plots the simulated motor/detent/friction torques and forces
  (dual y-axis: N·m on the left for motor/detent/bearing-friction, N on
  the right for the two linear friction ports) instead of position --
  saved as `torque_montage.png`. Simulation-only; there is no hardware
  torque sensor to compare against.
- `scripts/plot_tracking_error_montage.py`: same 10-panel chronological
  layout, plotting (measured − reconstructed commanded) and (simulated −
  reconstructed commanded) instead of raw position -- saved as
  `tracking_error_montage.png`. See "Tracking-error montage" below.
- `rendered_assets/`: generated by the scripts above; not hand-edited.
- `Parameter Optimization/model_parameters_optimization.json`: the Rev 4.2
  model's parameters partitioned into fixed, current-dependent (`T_hold`),
  and variable (LuGre friction, with proposed optimizer bounds) -- see
  its own `README.md` and "Current-dependent holding torque" below.

## What was run

Six configurations, run back to back in one ~39.6-minute session:

| Run | MRES | Current |
|---|---:|---:|
| 1 | 1/4 | 200 mA (50%) |
| 2 | 1/4 | 400 mA (100%) |
| 3 | 1/2 | 200 mA (50%) |
| 4 | 1/2 | 400 mA (100%) |
| 5 | 1/1 | 200 mA (50%) |
| 6 | 1/1 | 400 mA (100%) |

Each configuration runs, in this order: `BLOCK_0_START -> conditioning
(before C) -> C -> conditioning (before D) -> D_0.125 -> D_0.375 ->
D_1.25 -> D_3.5 -> D_9.5 -> D_27.5 -> D_70 -> D_200 -> BLOCK_0_END`, and
every block is preceded by its own amplitude-coded data-visible marker
signature (see `plot_full_raw_sequence.py`'s `find_block`/marker
handling, and `run_identification_dedicated_controller.py`'s
`TEST_MARKER_AMPLITUDES_FULL_STEPS` / `run_marker`).

## Segmentation

Block boundaries come directly from `identification_controller_log.csv`'s
timestamped `BLOCK_START`/`BLOCK_END` events, converted onto the IDS time
axis via the IDS file's own `Starttime of export` (Windows FILETIME) and
`SampleTime[ms]` header fields -- not inferred from the waveform shape.
Exact-match block names (`^D_9\.5$`, not a prefix/substring match) are
used throughout specifically to avoid confusing a real block with its own
preceding `MARKER_*`/`COND_BEFORE_*` separator, which was a real bug in
an earlier version of this pipeline.

## Investigation: Condition C measured trace does not track the commanded swing

**Symptom.** In the block montage's C panel, the measured trace sits at a
roughly constant +40 µm for nearly the entire ~123 s block, while the
commanded (red) trace shows the documented ±40 µm approach/return
pattern around 0. This was flagged as a possible polarity error.

**What was checked.** Run 1's C block was inspected directly against the
raw controller log (`identification_controller_log.csv`), not just the
plot:

```
t=  0.224s  MOVE_ACK  ideal_position_rev=-0.02000  label=positive_approach
t=  1.438s  MOVE_ACK  ideal_position_rev= 0.00000  label=positive_return
            [60 s dwell]
t= 61.658s  MOVE_ACK  ideal_position_rev= 0.02000  label=negative_approach
t= 62.889s  MOVE_ACK  ideal_position_rev= 0.00000  label=negative_return
            [60 s dwell]
```

This is `run_c()`'s documented design exactly: -4 full steps (-40 µm,
`positive_approach`), back to 0 (`positive_return`), dwell 60 s; then +4
full steps (+40 µm, `negative_approach`), back to 0 (`negative_return`),
dwell 60 s. **The controller's own logged command is correctly signed and
symmetric, and returns to 0 both times.** The `command_series()`
reconstruction used by the plots reads this log directly and reproduces
it faithfully -- there is no sign flip and no plotting-side bug in either
the raw log or the code that turns it into the red trace.

The measured trace, sampled every 5 s against this same timeline, tells a
different story:

```
t=  0.00s  commanded=  0.000 um  measured= -0.004 um
t=  5.00s  commanded=  0.000 um  measured= 39.691 um
t= 60.00s  commanded=  0.000 um  measured= 39.734 um
t= 65.00s  commanded=  0.000 um  measured= 40.449 um
t=120.00s  commanded=  0.000 um  measured= 40.398 um
```

The stage reaches ~+40 µm almost immediately (by t=5 s, i.e. right after
the first approach+return pair) and then stays there through the first
60 s dwell. A closer look at the subcondition-2 transition (fine-grained,
not the 5 s sampling above) shows it is not actually flat there either:
the measured trace spikes to a peak of **78.98 µm at t=61.36 s** (right
around `negative_approach`'s own timestamp, t=61.658 s), then decays back
down to ~40.4 µm by t≈70 s and stays there through the second 60 s dwell.
It never revisits anything near 0, and never visits -40 µm at all.

**Diagnosis.** This is not a polarity bug and not a plotting artifact --
the raw command log is correct, and the code faithfully reflects it. The
pattern that actually fits the data is that the fast ±4 full-step
reversal does not register as a genuine back-and-forth: the mechanism
only ever steps in the net-forward (positive) direction, not
backward-then-forward as commanded.

- **Subcondition 1** (`positive_approach` -40, `positive_return` +40):
  the stage does not visibly move backward first. Instead it registers a
  single net step from 0 to +40 µm -- consistent with the reversal
  direction failing to register while the forward step does, rather than
  with "approach fails, return succeeds" as two independent events.
- **Subcondition 2** (`negative_approach` +40, `negative_return` -40):
  the *approach* here commands the stage further in the same net-forward
  direction it is already sitting in (from 0 toward what would be +80 if
  it fully registered), producing the observed transient spike to
  ~79 µm -- but this settles back down to ~40 µm rather than holding at
  80 µm or returning to 0. The net effect of the whole second subcondition
  is no lasting change at all: a ~40 µm transient bump that decays, not a
  step.

In short: **the stage only ever steps forward, never backward-then-forward
as intended.** Subcondition 1 nets a real, permanent +40 µm step;
subcondition 2 produces only a transient ~40 µm bump on top of that
(peaking at +79 µm, decaying back to +40 µm) with no permanent second
step. The C block's creep/settling data for this run does not represent
the intended directional-approach probe and should not be used to fit
presliding/creep parameters as-is.

**Suggested next steps:**
1. Check the actual value of `CONDITIONING_FULL_STEPS_S` and the current/
   torque setting (`SC`) active during `run_c()` -- if the approach/return
   pair is commanded faster or at lower current than the stage can
   reliably reverse direction from rest, a forward-only bias (e.g. from
   backlash always being taken up in one direction, or a preload/gravity
   bias) is the expected failure mode.
2. Compare against `BLOCK_0_START`/`BLOCK_0_END`'s own small sub-moves
   (the ±1, ±4 full-step rungs of `REFERENCE_MOVES`) -- those blocks
   track their commands well (see `reference_repeatability_montage`
   style comparisons from the earlier pipeline), which would suggest the
   issue is specific to `run_c()`'s speed/current configuration rather
   than small full-step moves in general.
3. If confirmed as lost steps rather than a data issue, the current C
   block data does not measure what it was designed to measure (creep
   after a controlled small approach) and should be re-run with a slower
   approach/return speed or higher current before using it to fit
   presliding/creep parameters.
4. An independent motor-side check (e.g. a stall/step-loss detector, or
   simply listening/watching the stage during the approach move) would
   settle this directly.

## Investigation: D_3.5 and D_9.5 panels look wrong at coarser MRES

**Symptom.** In the block montages, `D_3.5` and `D_9.5` look like the
expected triangular ramp at MRES 1/4 (runs 1-2), but at MRES 1/2 and
MRES 1/1 they show a much shorter, jagged, non-triangular shape followed
by an unexplained trailing excursion that doesn't correspond to anything
in the command.

**Ruling out a plotting/data-extraction bug.** For run 3's `D_3.5` and
`D_9.5`, the raw controller log has exactly one (non-duplicated)
`BLOCK_START`/`BLOCK_END` pair each, zero `ERROR` events anywhere in the
9,685-row log, and the logged `speed_code`/`accel` values in the
`PLATEAU_START` detail field are byte-for-byte identical to run 1's:

```
run 1, D_3.5: speed_code=11, accel=decel=628, plateau_duration_s=20
run 3, D_3.5: speed_code=11, accel=decel=628, plateau_duration_s=20   (identical)
```

So `find_block()` is not picking up a stray/duplicate record, and the
Python driver issued the same nominal command in both runs.

**Confirming it against the controller's own ground truth.** The
controller's own `PLATEAU_START`/`PLATEAU_END` timestamps (not derived
from the IDS encoder at all) show the *commanded motion itself* completed
in a fraction of the expected time:

| MRES | D_3.5 duration | D_9.5 duration | D_27.5 duration | D_70 duration |
|---|---:|---:|---:|---:|
| 1/4 (runs 1, 2) | ~10.7 s | ~27.9 s | ~15.9 s | ~12.9 s |
| 1/2 (runs 3, 4) | ~1.6 s | ~2.9 s | ~15.8 s | ~12.1 s |
| 1/1 (runs 5, 6) | ~1.6 s | ~3.0 s | ~2.6 s | ~11.6 s |

This is a genuine execution-timing discrepancy, not a plotting artifact
-- the compression is visible directly in the controller's own event
timestamps, hours before any of this repo's plotting code ever touches
the data.

**Pattern.** The compression is consistent across both runs at each MRES
level (not a one-off glitch in a single run), and the *threshold* moves
predictably with MRES: nothing is compressed at MRES 1/4; `D_3.5` and
`D_9.5` are compressed at MRES 1/2 (but `D_27.5`/`D_70` are not); `D_3.5`,
`D_9.5`, and now `D_27.5` are all compressed at MRES 1/1 (but `D_70` is
not). The threshold rate rises as MRES gets coarser.

**Leading hypothesis (not confirmed).** `speed_code()` /
`configure_speed()` in `run_identification_dedicated_controller.py`
compute the `SS` speed code purely from the requested full-steps/s rate
and the constant `MOTOR_FULL_STEPS_PER_REV` -- there is no MRES term
anywhere in that calculation, so the script assumes the same code always
produces the same physical angular velocity regardless of microstepping
resolution. The data says otherwise. A rate-threshold that rises with
coarser MRES is exactly the signature of a controller with a fixed
minimum step-*pulse* rate it needs to sustain a smooth cruise: since
pulses/s = full-steps/s x MRES, a fixed minimum pulses/s floor implies a
minimum full-steps/s floor that scales as 1/MRES -- rising as MRES gets
coarser, matching the observed threshold shift exactly. Below that floor
for the active MRES, the controller apparently cannot sustain the
requested slow cruise and the move completes much faster than intended,
via some fallback/ramp-only behavior rather than the documented
ramp-cruise-decel profile.

This has not been confirmed against the controller's own documentation
(`docs/Stepper Motor Controller Command list.pdf`, referenced at the top
of the driver script but not machine-readable from this investigation) or
an independent motor-side timing check, so it should be treated as the
leading hypothesis, not a settled root cause. **Open question:** this
alone does not explain why the affected rate range is a narrow band
(`D_3.5`-`D_9.5` at MRES 1/2, extending to include `D_27.5` at MRES 1/1)
rather than every rate below the threshold in a simple monotonic sense --
worth re-checking once a candidate mechanism is confirmed.

**Practical implication:** `D_3.5` and `D_9.5` data (and `D_27.5` at
MRES 1/1) should not be used for Stribeck-curve fitting at MRES 1/2 or
1/1 without accounting for this -- the stage was not actually driven at
the intended commanded velocity for anywhere near the intended duration
in those cases.

## Fixed: controller-paced D-rate command reconstruction was a rendering artifact

**Symptom.** In `D_0.375` (and every rate `D_3.5` and above), the commanded
(red) line in the block montage jumped instantly from 0 to the full
plateau target, while the measured (teal) trace rose and fell over several
seconds in a rounded, triangular shape. This looked like the stage was
failing to track the command, but it was the opposite: the *plot* did not
reflect what the controller was actually told to do.

**Root cause.** Block D uses two genuinely different execution mechanisms
depending on rate (`run_identification_dedicated_controller.py`,
`SLOW_PLATEAU_RATES_FS_S = (0.125, 0.375, 1.25)` vs the rest):

- **Software-paced** (`0.125`, `0.375`, `1.25` full-steps/s,
  `run_slow_plateau_direction`): the host issues one `MR`/`MA` command per
  *single microstep*, timestamped individually. The logged `MOVE_ACK`
  stream already *is* the real commanded trajectory -- a genuine staircase
  of discrete pulses -- so a zero-order hold between consecutive events is
  exact. `D_0.375`'s "steppy" look at MRES 1/1 (only ~7-30 pulses spread
  over a 20 s plateau) is real hardware behavior, not an artifact.
- **Controller-paced** (`3.5`, `9.5`, `27.5`, `70`, `200` full-steps/s,
  `run_supported_plateau_direction`): the host issues a *single* `MR`/`MA`
  command for the entire plateau distance (accel + constant-speed + decel
  combined) and the controller executes its own ACCEL/CONST/DECEL ramp in
  hardware (`SS` with `ACCEL=DECEL=628`, `RAMPTYPE=1`). Only one
  `MOVE_ACK` is logged per direction, stamped at issue time with the
  *final* target -- the log never captures the intra-move trajectory. The
  old plotting code's zero-order hold between these two points therefore
  drew an instantaneous step where the stage actually took several seconds
  to ramp up, cruise, and ramp down.

The same zero-order-hold reconstruction fed `simulate_block_responses.py`'s
`theta_command`, so the LuGre simulation was being driven by an
instantaneous step input on every controller-paced rate -- producing a
spurious overshoot-spike-then-flatline in the simulated response that had
nothing to do with the model or the real command.

**Fix.** `scripts/command_reconstruction.py` reconstructs the
controller-paced case analytically instead of holding: it recomputes the
same ACCEL/CONST/DECEL shape the controller used
(`speed_code`/`plateau_duration_s`/`PLATEAU_ACCEL_CODE`, the same
constants and formulas as `run_supported_plateau_direction`), then
time-scales that shape so it starts and ends exactly on the two real
logged instants (this move's `MOVE_ACK` and the next real event, or the
block end). Scaling to the real elapsed time rather than trusting the
theoretical duration outright means the already-documented MRES-dependent
execution-timing anomaly above (`D_3.5`/`D_9.5`/`D_27.5` completing far
faster than commanded at coarser MRES) still reconstructs a
correctly-timed -- if compressed -- ramp rather than an overlapping or
out-of-order one; those rates remain separately marked and excluded from
analysis regardless. Software-paced rates are untouched: the per-pulse
`MOVE_ACK` stream is reconstructed exactly as before.

`plot_block_montage.py`, `plot_block_montage_with_simulation.py`, and
`simulate_block_responses.py` all now share this reconstruction. Every
affected D panel (`D_3.5` and above) is marked in-plot with a small
"† ramp reconstructed" note and a matching figure footnote explaining the
distinction; the LuGre simulation was rerun end to end against the
corrected command for all 66 (run, block) pairs.

## Legibility pass: trace priority, z-order, and the "commanded lags measured" check

**Visibility fix.** In `block_montage.png` and `block_montage_simulated.png`,
measured was drawn *before* commanded, so commanded's line sat on top and
could visually hide measured wherever the two crossed or briefly coincided
-- worst right at a block's start, where commanded's initial flat hold at 0
could paint over measured's real (and more important) early behavior. Both
scripts now draw in explicit priority order -- commanded (bottom, muted
grey, thin, dashed, low alpha) → simulated where present (middle) →
measured (top, full color, thicker) -- so the two priority traces are never
occluded by the least-important one, and every in-panel annotation (star,
cross, "ramp reconstructed" note) now sits on a translucent white backing
box so it stays legible regardless of what trace happens to pass under it.
`plot_torque_montage.py` got the same annotation-legibility treatment and
now also puts a legend on its first D panel (previously only the C panel
had one, far from the D block of panels).

**"Commanded starts after measured" check -- initial (incomplete) pass.**
The first check compared the reconstructed ramp's start time against when
the measured trace departs its baseline, using a 5%-of-peak threshold, and
concluded commanded generally led measured, chalking up the visible
residual to ordinary inertia/friction lag. That check was too coarse: a
5%-of-peak threshold on a slow quadratic ease-in measures curve *shape*,
not true onset, and it masked a real, much larger, and completely
different bug -- see below. Superseded by "Controller/IDS clock skew".

## Fixed: Controller/IDS clock skew (~0.32 s)

**Symptom.** After the visibility fix above made measured fully visible
again, a clear, consistent gap remained between the measured and
commanded/simulated onsets on non-excluded D panels -- e.g. `D_3.5` in
run 1, where measured departs from 0 and is already tens of µm in before
the reconstructed ramp (and the simulated trace, which is driven by the
same reconstruction) has moved at all.

**Root cause.** `identification_controller_log.csv`'s `utc` timestamps
come from the PC driving the dedicated controller (Python `datetime.now()`
at log-write time); `SteppingSequenceID.csv`'s timeline comes from the
*separate* Dewesoft acquisition PC's own clock (`Starttime of export`
FILETIME header). Nothing in this pipeline ever synchronized those two
clocks -- `ids_time_s = utc_timestamp - ids_start_epoch_s` implicitly
assumed they agreed. They don't, by a fixed, small amount.

**Calibration.** The very first Block 0 reference move is a fast, sharp,
isolated step (measured transition duration \<20 ms) with a precisely
known logged command time, making it an ideal calibration reference.
Comparing the logged `MOVE_ACK` time against the measured trace's
half-amplitude crossing time, across all 6 runs:

| Run | Logged move time (s) | Measured half-crossing (s) | Offset (s) |
|---|---:|---:|---:|
| 1 | 2.2220 | 1.9065 | +0.3155 |
| 2 | 2.2210 | 1.8973 | +0.3237 |
| 3 | 2.2229 | 1.9020 | +0.3209 |
| 4 | 2.2230 | 1.8988 | +0.3242 |
| 5 | 2.2210 | 1.9078 | +0.3132 |
| 6 | 2.2229 | 1.9068 | +0.3161 |

Mean **0.319 s**, standard deviation **4 ms** across 6 independent runs
spanning the ~40-minute session -- tight enough to rule out clock drift
over the session (which would trend, not cluster) and confirm a single
fixed offset: the controller PC's clock reads ~0.32 s ahead of the
Dewesoft PC's clock.

**Fix.** `CONTROLLER_CLOCK_SKEW_S = 0.319` subtracted in every script's
`load_log_rows()` (`plot_full_raw_sequence.py`, `plot_block_montage.py`,
`plot_block_montage_with_simulation.py`, `plot_tracking_error_montage.py`,
`simulate_block_responses.py`) when computing `ids_time_s`. Re-checking
the same calibration move after the fix: residuals of **-6 ms to +5 ms**
across all 6 runs -- within measurement noise.

**Scope and impact.** This is a single constant offset applied uniformly
to every log timestamp, so it does not change any *log-internal* timing
comparison (e.g. `PLATEAU_START`-to-`PLATEAU_END` durations used in the
D-rate execution-timing anomaly investigation above are unaffected -- both
timestamps shift by the same amount). It only affects where log-derived
block boundaries and the reconstructed commanded trajectory land relative
to the IDS-native measured waveform -- i.e. exactly the measured-vs-
commanded/simulated alignment in every montage. This predates the ramp-
reconstruction work entirely (the same `ids_time_s` computation has been
used since v3's pipeline was first built); it was only clearly exposed
once measured was drawn on top and commanded became a continuous ramp
instead of an instant step, both of which made a 0.32 s offset visually
obvious instead of hidden inside a single pixel-wide vertical line. The
full pipeline (`plot_full_raw_sequence.py`, both position montages, the
LuGre simulation, and the tracking-error montage below) was rerun against
the corrected timeline.

## Tracking-error montage

`scripts/plot_tracking_error_montage.py` renders, per run,
`rendered_assets/individual_subplots/run_0N_.../tracking_error_montage.png`
-- 20 panels (4 rows x 5 columns) in two chronological 10-panel blocks:

- **Top 10** (BLOCK_0, C, then the 8 D plateaus ascending): (measured −
  reconstructed commanded) and (simulated − reconstructed commanded), with
  a dashed zero-reference line. `command_reconstruction.py`'s
  `commanded_value_at()` evaluates the reconstructed commanded trajectory
  (hold or trapezoid, whichever applies) at each measured/simulated
  sample's own timestamp, so the subtraction is exact rather than
  interpolated.
- **Bottom 10** (same chronological order): (measured − simulated)
  directly -- model-vs-hardware fidelity, independent of the commanded
  trajectory. The simulated trace (sparser, non-uniform per solve_ivp
  segment) is linearly interpolated onto the measured trace's own dense,
  uniform IDS sample grid before subtracting.

One notable result: on the faster controller-paced D-rates, the simulated
trace tracks its own commanded input far more tightly than the real stage
does (e.g. run 1's `D_200`: simulated deviates from commanded by at most
~1.75 µm out of a ~12,000 µm swing, vs. measured deviating by up to
~1,900 µm) -- so the top-row simulated-error curve reads as a near-flat
line next to measured's much larger excursions on those panels, and the
bottom-row (measured − simulated) curve ends up nearly identical in shape
to the top-row measured-vs-commanded error, since simulated ≈ commanded
there. This is a real result, not a plotting artifact (checked
numerically): the current Rev 4.2 parameter set under-predicts real-world
tracking error at these rates.

Carries the same annotations as the position montages in both row blocks:
the C panel's star (did not track command -- error is expected to be
large there by design, not a defect) and the anomalous D-rate panels'
cross (excluded from analysis, since their command reconstruction is
itself execution-time-compressed).

## Current-dependent holding torque

**What changed.** Rev 4.2's `model_parameters.json` hard-codes one
`T_hold = 0.060 N*m` for every simulation, taken at the 400 mA nameplate
rating. But three of v3's six runs actually drove the motor at 200 mA
peak (`I_50pct`; the v2 BACKLOG specifies hold current equals run current
for every level), so those three runs were being simulated with double
their real holding torque. `simulate_block_responses.py` now derives
`T_hold` per run from its actual SC peak current:

```
T_hold(I) = sqrt(2) * K_t * I
K_t = T_hold_base / (sqrt(2) * I_rated_base) = 0.060 / (sqrt(2) * 0.400)
    = 0.10607 N*m/A
```

giving `T_hold(200 mA) = 0.030 N*m` and `T_hold(400 mA) = 0.060 N*m`
(unchanged from before, since 400 mA was already the nameplate baseline).
See `Parameter Optimization/model_parameters_optimization.json`'s
`current_dependent_parameters.T_hold` for the same numbers alongside the
rest of the model's parameter partition.

**How it enters the state-space equations.** `T_hold` only ever appears
through `k_em = N_r * T_hold` (`lugre_model_rev42.py`,
`build_structural_matrices`), which shows up in exactly two places:

- `K[0,0] = k_c + k_em` -- the rotor coordinate's (`theta_m`) own
  stiffness term.
- `B_theta = [k_em, 0, 0, 0, 0, 0]` -- the input vector multiplying the
  commanded angle `theta_cmd`, i.e. the generalized force is
  `k_em * (theta_cmd - theta_m) + ...` (the "motor torque" plotted in
  `torque_montage.png`).

Halving `T_hold` halves `k_em` (3.0 -> 1.5 N*m/rad at `N_r=50`) and
therefore halves the *input gain* `B_theta` exactly and linearly -- for
a given required electromagnetic torque, a smaller `k_em` demands a
proportionally larger rotor angle error `(theta_cmd - theta_m)` to
produce it. `K[0,0]`, in contrast, barely moves (71.75 -> 70.25, about
2%), because it's dominated by the coupling stiffness `k_c = 68.75`, not
`k_em` -- so the rotor mode's natural frequency is nearly unaffected;
what should change is steady-state tracking accuracy under a given
friction/detent disturbance, not resonant behavior.

**Observed effect (checked, not just asserted).** Comparing run 1 (50%
current, 200 mA) against run 2 (100%, 400 mA), same MRES, same `D_3.5`
command: motor torque came out essentially identical
(-4.56/+4.52 mN*m vs -4.55/+4.55 mN*m) and simulated peak stage position
differed by only ~0.12 µm out of ~700 µm (~0.02%). The mechanism above is
real, but its practical size is small for these plateau moves specifically
because `k_em`, even halved, remains far stiffer than what `D_3.5`'s
friction/inertia loads actually demand -- `theta_m` is tightly bound to
the downstream chain by `k_c` regardless of current, so neither current
level pushes anywhere near where the electromagnetic spring would become
the limiting stiffness. The correction is still applied everywhere (it's
the physically correct per-run value, not a nameplate approximation), and
the effect may be more visible on higher-torque-demand blocks (`D_200`,
`C`) where the required electromagnetic torque is larger relative to
`k_em` -- not exhaustively checked block-by-block here.
